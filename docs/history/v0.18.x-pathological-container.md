# v0.18.x Pathological Container Validation

This page records the `2026-06-30` physical-host pathological container pass
for the `v0.18.x` line.

Host:

- `192.168.1.12`
- `kyuubiki-lab`
- Ubuntu 24.04
- Docker `29.1.1`

## Scenario

The pass added and ran:

- `scripts/validation/pathological_container_validation.sh`
- `tests/pathological-containers/pathology_client.py`

The script builds or reuses the Linux dev image, starts one `gewyvern` runtime
container, then drives it from separate pathological client containers that:

- send truncated JSON sessions
- open and close empty socket sessions repeatedly
- slowly drip an incomplete JSON prefix before disconnecting
- send an oversized malformed line that trips the socket ingest line limit

This is a runtime-ingest fault validation, not a claim that passive eBPF packet
capture has fully classified arbitrary container traffic.

## Commands

```bash
SKIP_DOCKER_BUILD=true \
```

```bash
  target/validation/pathological-container
```

## Result

The generated evidence confirmed:

- the runtime starts healthy before injection
- malformed container clients flip `/health` to `resilience_degraded=true`
- `/v1/runtime/resilience.json` reports `status=degraded`
- `/v1/runtime/resilience.json` reports `severity=warning`
- `/v1/runtime/resilience.json` reports `socket_service.status=backing_off`
- a healthy template can still be ingested after the fault burst
- runtime logs preserve `socket_session_run_failed`
- runtime logs preserve concrete classes such as `unexpected_token`
- runtime logs preserve concrete classes such as `fact_line_exceeded_65536_bytes`
- scenario client logs are kept next to the runtime evidence bundle
