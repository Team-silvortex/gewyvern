This page is the concrete execution checklist for the planned `v0.16.x` line.
It is not a claim that the project has already moved past the current
`v0.15.4` checkpoint.

## Line Intent

`v0.16.x` exists to make the system easier to trust under drift pressure and
more convincing at first contact.

If `0.15.x` makes `gewyvern` feel usable and operationally coherent,
`0.16.x` should make it feel more protocol-shaped and evidence-shaped.

The line is successful only if another engineer can answer:

- what protocol families and entries are materially supported?
- what runtime/API/report evidence proves that support?
- what machine-facing surfaces are stable enough to build on?

without reverse-engineering the code every time.

The practical theme is:

- stronger protocol semantics
- stronger runtime evidence
- narrower ambiguity about what the system really knows

## Exit Checklist

### Protocol Semantics Contract

- [ ] at least one priority protocol cluster is materially deeper, not only
      wider
- [ ] healthy-path and failure-path semantics are both present for that cluster
- [ ] protocol surface, diagnosis hints, and failure semantics tell one story
- [ ] protocol directory/catalog outputs are stable enough for external control
      planes and history snapshots

### Runtime Evidence Contract

- [x] latest snapshots retain machine-readable protocol catalog artifacts
- [x] history snapshots retain machine-readable protocol catalog artifacts
- [x] history index can expose the latest protocol-catalog delta
- [ ] resilience evidence is part of the normal minor-line bundle, not an
      afterthought
- [ ] one operator can explain a runtime claim by pointing at archived evidence
      instead of terminal memory

### Event And Logging Contract

- [x] stable event names are centralized instead of scattered ad hoc strings
- [x] runtime, serve, DSL, diagnostics, API, and output failures all use the
      same event-naming discipline
- [ ] sensitive values are not casually copied into logs
- [x] log format examples exist in docs, not only in code

### Runtime Config Contract

- [ ] config schema/version handling is explicitly documented
- [x] upgrade and migration behavior is described with stable expectations
- [x] deprecated or legacy config paths have warning/compatibility rules
- [x] mutable-path policy remains explicit and non-ad-hoc

### Machine Surface Contract

- [ ] the narrow stable API/JSON core is named explicitly
- [ ] evolving versus stable report areas are named explicitly
- [ ] target routing and fetch paths are documented as contract or non-contract
- [ ] training dataset / analysis / summary surfaces are checked against that
      naming
- [x] protocol catalog and protocol surface endpoints are published as named
      machine surfaces

### CLI And Operator Contract

- [ ] primary CLI wording matches actual preferred flags
- [ ] compatibility aliases are either blessed or marked for removal later
- [ ] operator-facing docs stop implying hidden behavior that is not documented
- [ ] error/diagnostic wording is aligned with the current runtime behavior

### Test And Validation Contract

- [ ] contract-critical behavior has direct tests, not only transitive ones
- [x] config upgrade and runtime logging behavior have repeatable checks
- [ ] API/runtime contract checks exist for the fields we call stable
- [ ] packaged/container validation still passes after contract wording cleanup
- [ ] one repeated validation path exercises the stronger protocol-semantics
      cluster and archives the result cleanly

### Documentation Contract

- [ ] the documentation set names the stable core with less ambiguity
- [ ] the book, reference shelves, and release notes point to the same contract
      story
- [ ] the `0.16.x` line has its own historical snapshot once the line actually
      opens
- [ ] the line reads like a version theme, not a cleanup bucket

## Practical Rule

When deciding whether a task belongs in `0.16.x`, ask:

1. does it make protocol meaning materially stronger?
2. does it make runtime evidence materially easier to preserve or compare?
3. does it reduce ambiguity in a published surface?
4. does it make later `0.17.x` through `0.20.x` work less likely to re-open
   settled boundaries?

If not, it may still be useful work, but it is probably not central `0.16.x`
line work.

## Done Means

`v0.16.x` should feel done when:

- one protocol area feels noticeably deeper than before
- the runtime/history shelf can prove what protocol support existed at a moment
- the logs read like a named system
- the config behaves like a versioned contract
- the machine-facing core is narrower and easier to cite
- the docs stop hedging about surfaces that are already meant to persist

That is the point where the project can move into `0.17.x` with more attention
on `gewylang`, IR, and compiler maturity instead of repeatedly renegotiating
protocol/runtime truth.
