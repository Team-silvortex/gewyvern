# v0.15.x Minor Snapshot

This page records the meaning of the current `v0.15.x` line as a historical
minor snapshot.

Unlike `v0.14.x`, this line is not mainly about proving that the system is
coherent enough to use.

It is the line where that coherence starts being carried forward into runtime
layout, upgrade handling, and more explicit long-lived operational contracts.

## What v0.15.x Means

The `v0.15.x` line means:

- the standalone runtime should remain usable while its operational shape gets
  more explicit
- protocol breadth can continue growing without dissolving packaging and
  upgrade discipline
- `gewylang` and `gewyc` should keep feeling reusable, not experimental
- mutable runtime assets should stop depending on ad hoc path folklore

## What Was Already Whole Enough

By the time of `v0.15.x`, the project already had:

- a stable-enough diagnosis spine
- a documented read-only latest-snapshot API
- structured `gewylang` package and compiler surfaces
- Linux packaged validation and runtime validation evidence
- real multi-module collaboration evidence in containerized scenarios
- explicit resource-boundary hardening around the latest-snapshot API,
  external engine collaboration, and registry discovery

## What This Line Adds On Top Of v0.14.x

The `v0.15.x` line adds a more explicit operational spine:

- standard config/data/state/cache roots become first-class documentation
- legacy local layouts remain readable as upgrade safety fallbacks
- packaged share roots and repo-local development roots are treated as
  different roles rather than as one fuzzy path bucket
- future config/state persistence can now grow on a documented filesystem
  contract instead of scattering per feature

That is a deeper kind of maturity than just adding more protocol shelves.

## What Was Still Intentionally Incomplete

`v0.15.x` still leaves room for:

- more protocol-family depth
- richer compiler ergonomics
- cleaner explanation/reference material
- more mature collaboration surfaces across sibling projects
- fuller config-file and persisted-state semantics on top of the new runtime
  layout contract

But these are line improvements, not excuses for losing discipline.

The stable core still has to stay narrow, reviewable, and bounded.

## How This Differs From v0.14.x

`v0.14.x` asked:

- can this clearer project keep deepening without dissolving its boundaries?

`v0.15.x` asks:

- can that boundary discipline now survive real upgrades, packaging
  expectations, and explicit runtime-layout rules?

That makes `v0.15.x` an operationalization line, not just a maturity line.
