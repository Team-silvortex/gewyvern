# v0.20.x Minor Snapshot

This page records the meaning of the active `v0.20.x` line.

`v0.20.x` starts after the `v0.19.x` integration and convergence work proved
that the packaged release gate, the multi-project stack smoke, and the
pathological ingest gate can all run green as one repeatable posture.

The purpose of this line is to stop treating `1.0.0` as a vague destination
and instead behave like the final explicit pre-`1.0` seal.

## What v0.20.x Means

The line means:

- no casual widening of core runtime, API, report, or diagnosis surfaces
- release gates should stay repeatable as one routine, not only as remembered
  individual commands
- documentation should read like one system and point to one active release
  posture
- security and boundary checks should be part of ordinary ship judgment
- the stable core should be named clearly enough that `v1.0.0` is a direct next
  step instead of another convergence minor

## What This Line Inherits

By the time `v0.20.x` opened, the project already had:

- a packaged protocol catalog with family hubs, shelves, alias docs, and
  registry validation
- a green packaged `deb+rpm` release validation path
- a green multi-project Docker smoke across `leserpent`, `etragon`, and many
  `gewyvern` runtimes
- a green pathological ingest gate that preserves degraded-but-live runtime
  behavior under malformed clients
- runtime history, config, certificate, and lifecycle surfaces that now behave
  like release material rather than exploratory scaffolding

## Current Catalog Anchor

At this `0.20.x` checkpoint, the repository-level protocol shelf scans as:

- 70 protocol family directories under `protocols/`
- 363 packaged protocol entries under those family directories

Treat those numbers as the current catalog anchor for release-line docs and
validation notes. Older history pages may preserve smaller counts because they
describe earlier minor lines.

## What This Line Adds

The active work is to seal the core:

- freeze the preferred release judgment path around one repeatable gate
- reduce remaining wording drift between docs, CLI, reports, and API shelves
- name the stable core and the still-evolving edges more explicitly
- keep cross-project contracts green without reopening single-project drift
- preserve only the evidence that matters for a real `1.0.0` call

## Current `2026-07-11` Seal Checkpoint

At the current `v0.20.x` checkpoint, the release posture is green through the
full practical ship route.

The current observed green path includes:

What this means for the line:

- packaged `deb` and `rpm` artifacts currently validate in default mode
- the multi-project `leserpent + etragon + many gewyvern` topology currently
  survives container smoke and resilience checks
- pathological ingest currently degrades and recovers without wedging the
  runtime
- Rust, NuGet, and frontend dependency vulnerability checks are currently clean
- `leserpent` now has a dedicated security test shelf for remote token, loopback
  intent, persistence-import limit, and endpoint validation boundaries
- `etragon` daemon request handling now treats duplicate `Content-Length` and
  duplicate admin-token headers as explicit invalid-input cases instead of
  ambiguous-but-accepted requests
- the active question is now “what still prevents a stable surface freeze?” and
  not “do we have a real release gate yet?”
