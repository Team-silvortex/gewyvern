# `v0.15.x` To `v1.0.0` Roadmap

This page records the intended minor-line path from the current `0.15.x`
release line through `0.20.x`, with the explicit goal that `v1.0.0` should be
the next step after a healthy `0.20.x` close.

Use it when the question is:

- what is each remaining minor line supposed to accomplish?
- what should stop happening before `v1.0.0`?
- what must already be whole by the end of `0.20.x`?

Do not use this page as:

- the detailed current release gate
- the current `0.15.x` posture note
- the historical record for lines that have already closed

## The Planned Spine

The intended version spine is:

1. `v0.15.x`
2. `v0.16.x`
3. `v0.17.x`
4. `v0.18.x`
5. `v0.19.x`
6. `v0.20.x`
7. `v1.0.0`

The rule is deliberate:

- `0.15.x` through `0.19.x` are allowed to deepen and tighten the system
- `0.20.x` is the final pre-`1.0` sealing line
- `1.0.0` should not require another convergence minor after `0.20.x`

## Minor-Line Roles

### `v0.15.x`: Operationalization

This is the current line.

Its role is to make `gewyvern` feel intentionally usable under:

- runtime layout and upgrade pressure
- config and state persistence pressure
- logging and operator-triage pressure
- packaged/container validation pressure

By the end of this line, the project should already have:

- standard mutable roots
- conservative upgrade handling
- a more deliberate runtime log/config story
- a cleaner standalone operator surface

### `v0.16.x`: Contract Tightening

This line should turn scattered behavior into narrower published contracts.

Primary focus:

- stable event naming and logging surface discipline
- clearer machine-facing API / JSON guarantees
- config schema/version migration rules
- explicit compatibility boundaries for evolving versus stable surfaces

If `0.15.x` makes the runtime usable, `0.16.x` should make it easier to trust
what will not drift casually.

The working execution checklist for this line is:

- [docs/history/v0.16.x-checklist.md](/Users/Shared/chroot/dev/gewyvern/docs/history/v0.16.x-checklist.md)

### `v0.17.x`: Compiler And IR Maturity

This line should focus on the language/frontend/lowering spine.

Primary focus:

- more deliberate `gewylang` modularity
- safer lightweight inference and type-boundary behavior
- clearer IR evolution discipline
- better explain/debug surfaces for lowering and package composition

This is where the compiler side should stop feeling “promising” and start
feeling “reliably extensible”.

### `v0.18.x`: Protocol Depth And Runtime Confidence

This line should harden the protocol/runtime heart of the project.

Primary focus:

- deeper healthy-path and failure-path modeling across priority families
- grouped validation discipline
- multi-instance/runtime collaboration confidence
- stronger packaged and Docker-backed scenario evidence

This line is less about adding protocol vanity and more about making the
existing shelf feel strong enough for repetition and operator trust.

### `v0.19.x`: Integration And Freeze Preparation

This line should narrow churn and prepare for final sealing.

Primary focus:

- align docs, CLI, reports, and API wording
- settle compatibility aliases and stale shims
- reduce naming drift
- keep module boundaries explicit
- confirm the cross-project story with `etragon` and `leserpent`

By the end of `0.19.x`, the likely `1.0` surfaces should already be visible.

### `v0.20.x`: Final Pre-`1.0` Seal

This line should behave like the last explicit release-candidate minor.

Primary focus:

- no casual widening of core surfaces
- final surface freeze judgment
- final security/boundary pass
- final documentation-book coherence pass
- final package/container/runtime validation pass

The output of `0.20.x` should not be “we are close”.

It should be:

- the stable core is named
- the evolving/non-contract areas are named
- the release gate is repeatable
- the docs read like a system, not a lab notebook

## What Must Be True Before `v1.0.0`

Before the jump to `v1.0.0`, all of the following should already be true:

- the runtime, API, report, and diagnosis core surfaces are explicitly
  bounded
- event naming, config migration, and mutable-path policy are stable
- `gewylang` package composition and IR evolution rules are documented enough
  to build on purpose
- major protocol shelves feel deep enough to diagnose real module failures, not
  just match protocol identity
- validation is repeatable in local, packaged, and container-backed paths
- security posture is conservative by default and documented as such
- the documentation set reads as one coherent book with tutorial, how-to,
  reference, and explanation shelves all present

## What Should Stop Before `v1.0.0`

The following patterns should largely stop by the end of `0.20.x`:

- adding compatibility aliases without a retirement or blessing decision
- renaming public fields casually
- inventing new ad hoc mutable paths
- widening core report/API surfaces without explicit contract notes
- shipping important behavior that exists only in code, not in docs

## Practical Release Promise

If this roadmap holds, `v1.0.0` should mean:

- the project is not feature-complete forever
- but the core standalone debugger/runtime/compiler/reporting shape is mature
- and further work can happen on top of stable boundaries instead of by
  repeatedly renegotiating them

That is the bar this roadmap is aiming for.
