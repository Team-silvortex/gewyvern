## Repository Repair

The CI repair adds `Current artifact release packaging gate`, dependent on
both existing quality jobs. It runs the three explicit metadata commands and
the full default gate from a fresh checkout, without restoring package or
validation caches and with local Docker execution selected explicitly.

The CI consumer requires all five default stage booleans and the existing
`local_only / remote_missing` posture. It verifies the schema-v2 JSON/text
artifact-index publication IDs match, then archives packages, build metadata,
validation evidence, source commit, host toolchain information and the final
machine-readable gate result under a commit/run/attempt-specific name.
Evidence is also uploaded on failure; a failed job or partial upload is not
success. CI retention is 14 days; preserve accepted release evidence with the
release beyond that window.

The product job now audits npm with and without development dependencies.
The shared .NET CI warning policy additionally rejects NU1900 and NU1905;
the existing locked restores already enable transitive low-severity auditing.
No advisory is suppressed. The continuous-proof status cell indexes this CI
definition and audit note as source/documentation, not as new passed release
evidence. The historical seal and all product/protocol contracts stay intact.

## Reproduction

Use a fresh checkout of the exact candidate commit on a Linux host with Rust
1.98.0, .NET 10, Node 24, Docker daemon, curl and jq, with access to image,
toolchain, Cargo, npm, NuGet and advisory feeds. No remote-host credentials
are needed for this local CI shelf.

```bash
cargo dev version check
cargo run --quiet --locked --bin gewyvern_status -- validate
cargo test --locked --test project_status_tdd
cargo audit --no-yanked -D warnings
dotnet restore apps/leserpent/leserpent.slnx --locked-mode -p:ContinuousIntegrationBuild=true
dotnet test apps/leserpent/leserpent.slnx --no-restore --configuration Release -p:ContinuousIntegrationBuild=true
dotnet list apps/leserpent/leserpent.slnx package --vulnerable --include-transitive
npm ci --prefix apps/leserpent
npm audit --prefix apps/leserpent --json
npm audit --prefix apps/leserpent --omit=dev --json
mkdir -p target/validation
GEWY_DOCKER_EXECUTION=local cargo run --quiet --locked --bin gewyvern_validate -- \
  --json --json-out target/validation/ci-release-gate.json release-gate
```

Repeat the desktop locked restore/build from CI for its separate NuGet graph.
`dotnet list ... --vulnerable` is a report, not an exit-code-only vulnerability
gate; CI uses audited restore with warnings as errors. npm audit and RustSec
must actually reach their audit services. Restore/audit failure is not clean
dependency evidence.

Expected native artifacts on this x86-64 CI host are
`target/packages/gewyvern_2.1.2-1_amd64.deb` and
`target/packages/rpm/gewyvern-2.1.2-1.x86_64.rpm`.
Archive `target/packages/build-manifest.txt`, the gate JSON, all retained
component evidence and both `release-gate-artifacts.{json,txt}` with their
matching publication ID. Bind the final package digests and source commit
to any eventual release assets. Never substitute older packages.

For a combined release claim, repeat the gate explicitly with
`--leserpent-proof`; require both parity/recovery and schema-freeze stages.
For a physical-host claim use `--remote-host-validation` and preserve its
resolved host/target kind, ownership preflight/postflight, eBPF outcome,
integrity, timing and coverage signals. A VM runner cannot prove physical
Linux attach readiness. Do not change skip flags merely to obtain green CI.

## Outstanding External Evidence

The audit environment has no Cargo/rustup, .NET or Docker executables.
Consequently it cannot execute the repaired native gate or regenerate final
packages. Workflow syntax, embedded shell syntax, metadata inspection and
negative/positive CI result-consumption checks are local static validation;
they do not replace an executed packaging run.

Before calling the current candidate packaged-green, obtain a successful run
of the repaired job on the final commit, with both final packages and complete
current-run evidence. This is an execution gap, not a missing signing secret.

Additional evidence depends on the release claim:

1. **Physical Linux/eBPF:** an accessible physical target and SSH identity,
   attach/kprobe/tc privileges (or the documented privileged helper), correct
   route-device prerequisites, both workspace ownership fences and complete
   current-artifact attach evidence. Retain reported breadth/integrity/timing
   limitations; old fixtures are not a new candidate run. Two-host/two-kernel
   breadth remains the documented post-2.0 community advisory track, not a
   silently invented minimum for an ad-hoc community artifact.
2. **Native desktop/control artifacts:** rebuild the final versioned NativeAOT
   bundles, prove their install/upgrade/rollback and launch paths on supported
   hosts, and retain their actual hashes. If enabling deployment authority,
   retain the real C# to `leserpentd` deployment proof with the private socket
   and matching IPC token; transport failures must not select direct fallback.
   Reverse-bootstrap claims require current target/session/envelope-gated proof.
3. **Apple Developer ID/notarized release:** a macOS signing host with the
   fixed Apple tool inventory, usable Developer ID Application identity/private
   key and valid notary Keychain profile. Run `cargo dev package desktop
   --identity 'Developer ID Application: ORGANIZATION (TEAMID)'
   --notary-profile leserpent-notary`, retaining inside-out signing,
   notarization acceptance, stapling/ticket validation and Gatekeeper assessment
   for that same immutable final app. These are not prerequisites for the
   historically labeled ad-hoc MIT community artifact; it must remain explicitly
   non-notarized when these proofs are absent.
4. **Future hosted subscriptions only:** a reviewed production provider and
   final-bundle browser/vault account-lifecycle proof accepted with both
   `binary_bound=true` and `configuration_bound=true`. This is not a gate on
   existing MIT free-core capabilities.

There is no `2.1.2` release-ready conclusion in this audit. A passing local
packaging job proves precisely its local stages, with the native remote-missing
signal preserved, and is not an Apple, physical-host or final-publication proof.
