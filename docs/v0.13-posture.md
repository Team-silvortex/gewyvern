# v0.13.0 Posture

This note defines the intended posture of `gewyvern` in the current `v0.13.0`
preparation line.

`v0.13.0` is not the final `1.0.0` claim.

It is the point where the project should already feel complete enough to begin
real use on purpose:

- the runtime should be coherent
- the compiler and DSL should be coherent
- the report and machine-facing outputs should be coherent
- the documentation should be coherent
- the security and exposure boundaries should be explicit

In other words:

`v0.13.0` does not need to be the forever-frozen final form, but it should be
whole enough that another engineer can pick it up, use it, and extend it
without guessing what the project is supposed to be.

## What v0.13.0 Should Mean

The `v0.13.0` line should be interpreted as:

- usable
- documentable
- reviewable
- bounded
- intentionally scoped

It should not be interpreted as:

- feature-complete across every protocol family
- permanently frozen in every output detail
- a broad observability platform
- a license to widen surfaces again without discipline

## Who Should Be Able To Use It

By the time the `v0.13.0` line closes, the following readers should be able to
work successfully from the repository itself:

- an operator running the CLI or `--serve`
- an engineer reading `summary.json` / `analysis.json`
- a DSL author writing or debugging a gewy package
- a contributor extending runtime or reporting behavior

If one of those people still needs tribal knowledge to succeed, the project is
not yet in the right `v0.13.0` posture.

## What Must Already Be Whole

### Runtime

- single-target scans should be understandable
- full sweeps should be understandable
- `--serve` plus API behavior should be documented and bounded
- packaged/runtime validation should already exist and be repeatable

### DSL / Compiler

- the preferred `gewylang` subset should be explicit
- package shape should be explicit
- `gewyc` outputs should be documented enough for practical use
- module/function composition should be predictable enough to reuse

### Reports / Machine Output

- the narrow machine-facing contract should be clear
- operator-facing HTML/summary behavior should be coherent
- conservative diagnosis semantics should be intentional, not accidental

### Security / Boundaries

- ingest trust and exposure posture should be documented
- sidecar/external analysis should remain additive, not sovereign
- known resource/safety boundaries should be bounded in code and described in
  docs

### Documentation

- there should be a shortest path
- there should be a tutorial path
- there should be a task-oriented path
- there should be exact lookup pages
- there should be explanation pages

That is the reason the documentation is now being organized as a book-shaped
set instead of a flat pile of notes.

## What Can Still Be Incomplete

The `v0.13.0` line can still leave some things intentionally unfinished:

- protocol breadth can continue growing later
- HTML presentation can still evolve
- augmentation internals can still evolve
- nearby collaboration layers can still mature
- some deeper tutorials can still be thin, as long as the reading path is
  already clear

The key distinction is:

- missing polish is acceptable
- missing shape is not

## Practical Rule

When deciding whether a change belongs in the `v0.13.0` line, ask:

1. does this make the current system clearer, safer, or more usable?
2. does this reduce ambiguity for operators, DSL authors, or contributors?
3. does this help the project feel more whole without widening the surface?

If the answer is yes, it likely belongs here.

If the change mostly widens scope, adds novelty, or makes the surface more
open-ended, it probably belongs after the `v0.13.0` convergence line.

## Relationship To 1.0

`v0.13.0` should make `v1.0.0` a release judgment question, not a discovery
question.

By the end of this line, the repository should already make it obvious:

- what `gewyvern` is
- what it is not
- how to use it
- how to extend it
- what is stable
- what is still evolving

That is the standard for “not yet final, but already complete enough to start
using with intent”.
