# 1.0 Readiness

This note turns the current pre-`1.0` discussion into a practical checklist.

It is intentionally short.

The goal is not to restate the whole roadmap. The goal is to answer:

- what already looks `1.0`-worthy
- what still blocks a `v1.0.0` claim
- what should happen in `v0.10.0`

For the broader milestone path, see
[ROADMAP.md](/Users/Shared/chroot/dev/gewyvern/ROADMAP.md).

## Current Assessment

`gewyvern` is very close to `1.0`, but it should not claim `v1.0.0` yet.

The current recommended posture is:

- `v0.9.x`
  - active surface-freeze and operational-hardening line
- `v0.10.0`
  - final pre-`1.0` validation and contract-freeze line
- `v1.0.0`
  - only after the items below are explicitly closed

## What Already Looks 1.0-Ready

### Architecture

- the runtime/compiler/reporting split is clear and documented
- `main`, `serve_runtime`, `report_runtime`, `diagnosis_runtime`,
  `data_api`, and `external_analysis` already look like long-lived module
  boundaries
- `gewyvern` can stand on its own without requiring an external diagnosis
  sidecar

### Diagnosis Spine

The core operator-facing diagnosis model is already strong enough to anchor a
`1.0` contract:

- `primary_module_kind`
- `primary_failure_stage`
- `primary_failure_mode`
- `primary_failure_detail`
- `primary_failure_confidence`
- `primary_failure_basis`
- `ambiguous`
- `competing_hypotheses`
- `operator_guidance_*`

### Operational Shape

- the default ingest and API posture is now safer by default
- the standalone CLI / `--serve` / API / report flow is coherent
- performance baselines exist for the main hot paths

## Current 1.0 Blockers

These are the things that still make a `1.0` claim premature.

### 1. Public Surface Wording Still Says "Stable Enough"

Today the public docs still frame the main surfaces as:

- stable enough for `v0.9.x`
- not yet a forever compatibility promise

That is correct for `0.9`, but it means we have not yet made the stronger
promise that `1.0` implies.

Before `v1.0.0`, we should replace this wording with an explicit contract:

- which CLI flags are stable
- which JSON/API fields are stable
- which areas are intentionally not part of the compatibility promise

### 2. Transitional CLI Aliases Still Exist In The Primary Surface

The CLI still accepts transitional aliases such as:

- `--socket-trust`
- `--allow-remote-socket`
- earlier implementation-specific external-engine aliases

That means the command surface is not fully frozen yet.

Before `v1.0.0`, we should choose one of two paths:

1. remove them and keep only the generic preferred names
2. formally bless them as supported compatibility aliases

What we should avoid is carrying them into `1.0` as "temporary, but still in
help output".

The current recommended split is:

- keep as supported compatibility aliases:
  - `--socket-trust`
  - `--allow-remote-socket`
- remove before `v1.0.0`:
  - implementation-specific external-engine aliases such as the old
    `--etragon-*` names

Rationale:

- the socket flags are historical but still describe a real operator transition
  path into the newer ingest-mode model
- the `--etragon-*` names leak a specific sibling implementation into the main
  `gewyvern` product surface, which is the opposite of the intended generic
  external-engine boundary

### 3. The Stable Contract Needs A Narrower Published Core

The diagnosis spine is in good shape, but some surrounding output is still
documented as evolving:

- exact HTML layout
- parts of `report.json`
- augmentation `data` internals

That is acceptable, but `v1.0.0` should make the boundary sharper:

- stable core:
  - summary diagnosis spine
  - analysis snapshot spine
  - target indexing and path-segment routing
- evolving presentation:
  - HTML wording/layout
  - auxiliary report decoration
  - pass-specific augmentation payload internals

### 4. Release Discipline Needs One Intentional Freeze Pass

The project has already done a lot of real hardening, but a `1.0` claim should
follow one explicit release-minded pass that prioritizes:

- deleting or settling obvious compatibility shims
- removing naming drift
- checking doc/CLI/help/report consistency
- confirming the published stable surfaces match the real code

This should be a dedicated `v0.10.0` activity, not something assumed to be
"probably already true".

## Suggested v0.10.0 Exit Checklist

The following checklist is a good practical bar for saying "`v1.0.0` is next".

### Surface Freeze

- [x] preferred CLI flags are the only flags shown in the primary help path
- [x] socket-ingest legacy aliases are explicitly declared supported
- [x] implementation-specific external-engine aliases are removed from the main
      CLI surface and parser before `v1.0.0`
- [x] `summary.json` stable fields are published as a real compatibility
      contract candidate
- [x] `analysis.json` stable fields are published as a real compatibility
      contract candidate
- [x] API target-routing and `target_refs[].path_segment` behavior is explicitly
      declared stable

### Contract Clarity

- [x] `surface-stability.md` is rewritten from "`v0.9.x` stable enough" to a
      contract-candidate note
- [x] evolving/non-contract areas are explicitly listed
- [x] operator guidance semantics are documented as first-class built-in output

### Operational Confidence

- [x] `--serve` + API + external-engine hook behavior is documented with
      restart, failure, and degraded-mode expectations
- [x] benchmark baselines are refreshed and accepted for release-candidate use
- [x] no known critical safety or resource-boundary issues remain open

Current assessment for that item is intentionally narrow and concrete.

It means that, in the current tree, the main standalone paths already have
explicit guards for the classes of failures that previously looked most likely
to block a `1.0` claim:

- socket ingest applies line and fact-count limits during read, rather than
  after unbounded accumulation
- Unix sockets are created with restricted permissions
- remote API exposure remains explicitly opt-in
- slow API clients are handled independently and bounded by read timeout
- external-engine execution is bounded by timeout, output caps, augmentation
  caps, and cache limits
- protocol/profile discovery avoids symlink recursion and repeated-directory
  loops

This is a current release-candidate assessment, not a forever guarantee that no
future safety issues can appear.

### Release Hygiene

- [x] obvious compatibility wrappers and stale entrypoints are deleted or
      explicitly retained with intent
- [ ] docs no longer contradict runtime behavior
- [ ] a final release-candidate pass is run with "no churn in core surfaces" as
      the rule

## Practical Recommendation

The healthiest path is:

1. keep `v0.9.x` focused on disciplined stabilization
2. use `v0.10.0` as the explicit contract-freeze and release-candidate line
3. move to `v1.0.0` only after this checklist is closed on purpose

That keeps the jump to `1.0` honest.

It also matches the current state of the codebase:

- much stronger than a casual `0.x`
- not quite at "we are ready to promise this surface long-term" yet
