# v0.14.0 Posture

This note defines the intended posture of `gewyvern` in the current `v0.14.0`
line.

`v0.14.0` is not an experimental convergence line. It is an active
`0.14.x` release line that should already feel coherent, usable, and bounded.

It should be possible for another engineer to:

- run the runtime with intent
- read the diagnosis spine with confidence
- author or debug a `gewylang` package
- extend runtime or reporting behavior without guessing what the project is
  supposed to be

## What `v0.14.0` Should Mean

The `v0.14.0` line should be interpreted as:

- usable
- documentable
- reviewable
- bounded
- intentionally scoped

It should not be interpreted as:

- feature-complete across every protocol family
- a broad observability platform
- a control plane
- a promise that all presentation details are frozen forever

## Who Should Already Be Able To Use It

The following readers should be able to work successfully from the repository
itself:

- an operator running the CLI or `--serve`
- an engineer reading `summary.json` / `analysis.json`
- a DSL author writing or debugging a gewy package
- a contributor extending runtime or reporting behavior

If one of those people still needs tribal knowledge to succeed, the current
line is not in the right posture yet.

## What Must Already Be Whole

### Runtime

- single-target scans should be understandable
- full sweeps should be understandable
- `--serve` plus API behavior should be documented and bounded
- packaged/runtime validation should exist and be repeatable

### DSL / Compiler

- the preferred `gewylang` subset should be explicit
- package shape should be explicit
- `gewyc` outputs should be documented enough for practical use
- module/function composition should be predictable enough to reuse

### Reports / Machine Output

- the narrow machine-facing contract should be clear
- operator-facing HTML/summary behavior should be coherent
- conservative diagnosis semantics should be intentional, not accidental

### Security / Boundaries

- ingest trust and exposure posture should be documented
- sidecar/external analysis should remain additive, not sovereign
- known resource/safety boundaries should be bounded in code and described in
  docs

### Documentation

- there should be a shortest path
- there should be a tutorial path
- there should be a task-oriented path
- there should be exact lookup pages
- there should be explanation pages

## Current Evidence

This posture is not just aspiration, but this section should still stay at the
"why the claim is justified" level rather than becoming the detailed findings
ledger.

The current tree already has concrete validation evidence behind it:

- the full built-in protocol registry is green
- packaged Linux installs work after real install steps
- packaged standalone runtime validation works in clean containers
- packaged protocol/operator-path validation works in clean containers
- release-style packaged Linux checklists already pass as one routine
- the current three-module collaboration topology already works in Docker

## What Can Still Evolve

The `0.14.x` line can still evolve in healthy ways:

- protocol breadth can continue growing
- HTML presentation can continue improving
- collaboration layers can continue maturing
- deeper tutorials can still be expanded
- language ergonomics can improve as long as core boundaries stay disciplined

The key distinction is:

- missing polish is acceptable
- missing shape is not

## Practical Rule

When deciding whether a change belongs in the current line, ask:

1. does this make the current system clearer, safer, or more usable?
2. does this reduce ambiguity for operators, DSL authors, or contributors?
3. does this strengthen the current `0.14.x` posture without bloating the core?

If the answer is yes, it likely belongs here.

If the change mostly widens scope, adds novelty, or confuses the standalone
runtime posture, it probably belongs in a later line.
